## Context

集团信贷业务目前没有统一的智能化决策平台。审批依赖人工经验和分散在各业务系统中的硬编码规则，无法满足以下需求：
1. 业务量增长带来的自动化决策需求（日均数十万笔申请）
2. 银保监会对决策可追溯、可解释、可审计的监管要求
3. 风控策略快速迭代的需求（策略师期望自助配置，而非依赖开发排期）
4. 模型（评分卡、反欺诈）与规则协同决策的需求

当前状态：绿地项目，无遗留系统约束。已有规格文档定义了四大平台（大数据、决策引擎、模型、运维）的功能范围。

约束条件：
- 集团内部使用，非 SaaS
- 大型规模：日增 >5000万条，存储 >50TB
- 技术栈已确定：Java 17+ / Spring Boot 3.x / Vue 3 / Hadoop / Flink
- 决策引擎必须自研，不依赖第三方商业授权

## Goals / Non-Goals

**Goals:**

1. 构建完整的大数据平台，实现数据从采集、存储、计算到服务的全链路闭环
2. 构建自研决策引擎，支持 5 种规则类型 + DAG 决策流 + 数千变量管理 + AB 实验 + 可解释性追踪
3. 构建模型平台，管理 ML 模型全生命周期（训练→评估→部署→监控）
4. 提供可视化编辑器（Vue），业务人员可自助配置规则、评分卡和决策流
5. 满足单笔决策 P99 < 3s、单机 QPS ≥ 500 的性能目标
6. 满足监管合规：决策日志保留 5 年、完整审计追踪、高可解释性

**Non-Goals:**

1. 不做多租户/SaaS化（仅集团内部使用）
2. 不做 CEP 复杂事件处理（不是实时流式决策场景）
3. 不做深度学习模型训练平台（仅支持 LR/XGBoost/LightGBM 传统评分模型）
4. 不做实时决策可视化（如实时大屏，这是 BI 平台的职责）
5. 不做 BPMN 工作流引擎（审批流程不在决策引擎范围内，由业务系统负责）
6. 不做数据交易所或数据对外输出

## Decisions

### DEC-01: 决策引擎自研，不采用开源方案

**决策**: 完全自研决策引擎核心，不基于 LiteFlow/Drools/URule 等开源或商业规则引擎。

**理由**:
- LiteFlow 是组件编排引擎而非规则引擎，缺少评分卡/决策表/规则匹配，65% 业务逻辑仍需自研
- Drools 学习曲线极陡（DRL/RETE），国内人才稀缺，最好工具需 Red Hat PAM 商业授权
- URule Pro 需商业授权，开源版 2018 年停更，供应商锁定风险高
- 自研虽然开发量最大，但完全可控、无授权风险、可按需定制

**权衡**: 开发周期增加约 30%，但获得完全自主可控性。最坏情况下，如果某个模块质量不达标，可以局部替换（如用 Drools 替换规则匹配模块），因为 engine-core 与业务层解耦。

### DEC-02: 编译执行模型 — AST 解释器，不用字节码生成

**决策**: 规则 JSON 编译为 AST（抽象语法树），执行时遍历 AST 求值。不使用 ASM/Javassist 字节码生成。

**理由**:
- 决策引擎的瓶颈在数据获取（网络 IO 约 800ms），不在规则执行（CPU 约 5-10ms）
- AST 解释器性能完全足够（200 条规则 ≈ 5-10ms）
- AST 天然支持可解释性追踪（每个节点就是一个追踪点）
- 字节码生成开发复杂度高、调试困难、某些 JVM 环境限制动态字节码

**替代方案**: 字节码生成可提供接近原生 Java 的性能，但收益（省几毫秒）不值得付出的复杂度。

### DEC-03: 表达式引擎使用 Aviator

**决策**: 使用阿里开源的 Aviator 作为规则条件求值引擎。

**理由**: 金融行业大量验证；支持编译缓存（`compile()` → `AviatorExpression` → Caffeine）；支持自定义函数注册；轻量无安全漏洞风险（对比 Groovy 历史漏洞）。

**替代方案**: MVEL（略快但社区小）、Groovy（太重且有安全风险）。

### DEC-04: engine-core 纯 Java，不依赖 Spring Framework

**决策**: 决策引擎核心模块（`engine-core`）使用纯 Java，不引入 Spring 依赖。

**理由**:
- 引擎核心可以被任何 Java 框架使用（Spring Boot / Quarkus / 纯 Java Main）
- 便于单元测试（不需要 Spring 上下文）
- 降低依赖复杂度，引擎核心只依赖 Jackson + Aviator + Caffeine
- 与管理后台（`decision-admin`，Spring Boot）完全解耦，并行开发

**影响**: 数据源访问（Redis/HBase/MySQL）通过 Provider 接口抽象，在 `decision-server` 层注入具体实现。

### DEC-05: DAG 决策流 — 自研轻量执行器，不引入工作流引擎

**决策**: 决策流编排自研轻量 DAG 执行器，不引入 Activiti/Flowable 等重型 BPMN 引擎。

**理由**:
- 信贷决策流是确定性的流程（每次执行走完即结束），不需要持久化流程实例
- 不需要人工任务节点（审批由业务系统负责）
- 自研 DAG 执行器可以深度优化性能（并行执行、变量预取）
- 避免引入重型框架的运维负担

**实现**: DAG 拓扑排序 + CompletableFuture 并行执行 + 条件边求值。约 500-800 行核心代码。

### DEC-06: 变量 4 层分层 + 预取优化

**决策**: 变量按来源分为 4 层（输入/外部/缓存/衍生），请求进入时按 DAG 静态分析所需变量，分层并行预取。

**理由**: 2000+ 变量不可能也不需要全部获取。预取确保：
- 外部 API（最慢 800ms）全部并行调用，总耗时 = max
- 缓存变量（Redis/HBase）批量获取
- 衍生变量懒计算（用到才算）

**替代方案**: 全量预取（浪费）、完全懒加载（无法并行外部 API，总耗时 = sum）。

### DEC-07: 前端 DAG 画布使用 AntV X6

**决策**: 决策流设计器基于蚂蚁开源的 AntV X6 构建。

**理由**: 金融场景广泛验证；自定义节点能力强（可定制规则/评分卡/模型等节点样式）；MIT 协议；Vue 3 集成方案成熟。

**替代方案**: LogicFlow（百度，功能稍弱）、jsPlumb（商业+开源混合协议）。

### DEC-08: 规则热加载 — Caffeine + MQ 广播

**决策**: 规则编译产物缓存在 Caffeine 本地缓存，变更时通过 MQ（RocketMQ）广播到所有引擎节点。

**理由**:
- Caffeine 是 Java 生态性能最优的本地缓存
- MQ 广播确保多节点一致性（对比 ZK/Nacos 方案，MQ 更简单可靠）
- CopyOnWrite 语义：正在执行的请求继续用旧版本，新请求使用新版本

### DEC-09: 数据分层架构 ODS → DWD → DWS → ADS

**决策**: Hive 数仓采用四层分层架构。

**理由**: 金融行业标准分层模式；每层职责清晰（原始→清洗→汇总→应用）；支持跨层数据质量校验；便于数据血缘追踪。

### DEC-10: 10 人团队 / 4 阶段 / 12 个月交付

**决策**: 10 人团队分 4 阶段（基础设施→核心引擎→引擎完善→模型联调上线）交付。

**理由**:
- Phase 0-1 先打通数据管道和引擎核心，尽早验证端到端可行性
- Phase 2 补全业务能力（AB实验、外部数据、沙箱）
- Phase 3 模型平台独立开发，最后联调
- 每阶段有明确的交付物和验收标准，降低整体风险

## Risks / Trade-offs

### [R1] 可视化编辑器开发量超预期 → 高概率、高影响

编辑器涉及 4 个复杂组件（规则编辑器、评分卡编辑器、决策表编辑器、DAG 设计器），预计 3-4 个月。

**缓解**: 使用 AntV X6 + Handsontable 减少自研量；先做规则编辑器和 DAG 设计器（核心），决策表和评分卡编辑器可简化版先上线再迭代。

### [R2] 引擎性能不达标 → 中概率、高影响

单机 QPS 500 / P99 3s 的目标需要精心优化。

**缓解**: Phase 1 就建立 JMeter 性能基准测试；引擎开销目标 <50ms（把预算留给数据获取）；最坏情况通过水平扩展解决（4 台机器 × QPS 250 = QPS 1000）。

### [R3] 数千变量管理复杂度爆炸 → 高概率、中影响

2000+ 变量的注册、版本、依赖、血缘管理是 Feature Store 级别的问题。

**缓解**: 变量分域管理（征信/工商/运营商/内部/衍生）；变量版本化，规则绑定到具体版本；自动依赖分析，变更时评估影响范围。

### [R4] 外部 API 不稳定 → 高概率、中影响

征信/工商等外部 API 可能超时、限流或变更。

**缓解**: 统一的 API 适配器层（超时 3s + 重试 1 次 + 降级到缓存）；Redis 缓存热点查询结果（TTL 可配置）；Mock 模式支持离线测试。

### [R5] 大团队协作效率 → 中概率、中影响

10 人同时开发，模块边界不清可能导致互相等待。

**缓解**: engine-core 纯 Java 解耦设计确保引擎组和后台组独立；清晰的接口契约先定 API 再实现；前后端分离 + Mock 数据开发；双周集成演示。

### [R6] 自研引擎质量风险 → 低概率、高影响

自研 AST 解释器可能存在边界条件 bug。

**缓解**: 目标单测覆盖率 ≥80%；沙箱回测用历史数据验证；灰度发布机制（新规则先跑 5% 流量验证）。

## Migration Plan

绿地项目，无迁移需求。部署策略：

1. **Phase 0**: 基础设施集群搭建（Hadoop/Kafka/Flink/Redis/HBase/ES）
2. **Phase 1**: 决策引擎 MVP 上线（使用 Mock 外部数据和 Mock 模型）
3. **Phase 2**: 外部数据源逐个接入（先征信，后工商/司法等）；正式模型部署
4. **Phase 3**: 灰度上线 — 新系统与旧人工审批并行运行，新系统结果仅作为辅助参考
5. **全量切换**: 灰度验证通过后，新系统作为主决策通道

**回滚策略**: 每次发布保留上一版本的编译产物缓存，支持一键回滚到任意历史版本。

## Open Questions

1. **外部 API 的 SLA 合同**: 各外部数据源（征信/工商等）的 API 调用频率限制和 SLA 需要与供应商确认，直接影响变量预取策略和降级方案
2. **监管审计具体要求**: 银保监会对决策日志的格式、保留期限、可解释性级别是否有具体的规范性文件？需要与合规部门确认
3. **现有业务系统的数据格式**: MySQL/Oracle 中的业务表结构是否已经标准化？数据质量如何？需要做详细的数据盘点
4. **模型工程师的技能水平**: 模型平台的自助化程度取决于模型工程师的技术能力（能否写 Python？能否配置超参数？）
5. **K8s 集群规模**: 生产环境的 K8s 集群规模和资源配额需要根据压测结果确定
